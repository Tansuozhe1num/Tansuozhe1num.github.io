核心API

Redisson 最值得掌握的 API，可以按用途分成以下几类。

业务场景 核心 API 典型用途
普通缓存、对象存储 RBucket 缓存用户信息、开关配置、幂等标记
Hash、带过期时间的 Map RMap、RMapCache 用户属性、分布式缓存
Set、List、排序集合 RSet、RList、RScoredSortedSet 去重、列表、排行榜
原子计数 RAtomicLong 计数器、序号
分布式锁 RLock 防止并发重复操作
公平锁、读写锁 RFairLock、RReadWriteLock FIFO 加锁、读写互斥
信号量 RSemaphore 限制同时执行的任务数
分布式限流 RRateLimiter 接口限流、控制调用频率
队列 RQueue、RBlockingQueue 等 任务传递、生产者消费者
发布订阅 RTopic 消息通知、事件广播
分布式计数与同步 RCountDownLatch 多个任务汇合、等待初始化

这里有一个重要区别：分布式数据结构解决数据共享问题，分布式同步器解决多个应用实例之间的并发协调问题。 例如，RMap 适合保存共享数据，而 RLock 适合协调多个服务实例对同一业务资源的操作。

二、引入依赖与连接 Redis

2.1 Maven 依赖

如果只想使用 Redisson 核心 API，推荐先引入 redisson，自己管理客户端 Bean，适合学习以及需要精确控制 Redis 连接的 Spring Boot 项目。

这里用的是 Redisson 3.x 的示例版本。实际项目应根据 Java、Spring Boot、Spring Data Redis 版本选择兼容版本，不要直接把最新版 starter 塞进旧项目。Redisson 官方将其 Spring Data 适配模块分别对应 Spring Boot 2.x、3.x 和 4.x。

如果希望 Spring Boot 自动装配，可以使用 redisson-spring-boot-starter，但要注意其版本与项目现有依赖的兼容性。

3.2 RMap：操作类似 Hash 的数据

RMap<K,V> 是分布式 Map，适用于共享属性、按字段读写的数据。

如果不需要获取更新前的旧值，可以使用 fastPut()、fastRemove() 这类方法，减少不必要的返回数据。

注意：RMap 本身不是普通 Java 内存中的 HashMap，每次操作都可能涉及网络通信。

3.3 RMapCache：每个字段单独设置过期时间

这几个接口与 Java 集合的使用思路类似，但数据共享在 Redis 中。

集合内部的具体实现和复杂度仍由对应的 Redis 结构决定，不要把分布式集合误认为一个没有网络成本的本地集合。

3.6 RAtomicLong：分布式原子计数器

计数器存储在 Redis 中，可以被多个 JVM 共享。像 incrementAndGet() 这样的原子操作适合计数、简单序号等场景。

但是，多个不同的 Redis 操作组合起来，并不自动构成一个整体原子事务。例如先检查库存，再扣减库存，不能仅仅因为使用了 RAtomicLong 就认为整个流程没有竞态。

四、分布式锁：Redisson 最重要的功能

在单体应用中，synchronized 可以协调同一个 JVM 内的线程，但不能直接协调部署在不同机器上的 JVM。

Redisson 的 RLock 提供基于 Redis 的分布式可重入锁，并支持通过发布订阅唤醒等待者。

4.2 看门狗机制是什么？

Redisson 默认的锁看门狗超时值为 30 秒。当客户端持有锁并且仍然正常运行时，看门狗会续期，避免锁仅因初始 TTL 到期而被释放。具体超时参数可以由 lockWatchdogTimeout 配置。

理解这几个概念：

概念 含义
等待时间 调用方愿意等待多久来获取锁
租约时间 锁最多允许持有多久
看门狗 对未指定固定租约的锁自动续期
unlock() 释放当前线程持有的锁

锁必须在 finally 中按持有情况释放。RLock 的所有权与线程关联，其他线程不能直接替持有者解锁。

MultiLock 与 RedLock

错误一：锁名称没有绑定业务资源。

错误二：直接使用固定租约，却不考虑耗时。

如果业务运行超过固定租约，其他实例可能再次拿到锁。业务必须考虑租约、执行时间和并发安全问题。

错误三：在不持有锁的情况下解锁。

这可能触发 IllegalMonitorStateException。始终在 finally 中先判断当前线程是否持有锁。

错误四：认为加锁能代替数据库事务。

分布式锁不是数据库事务。数据库仍然需要正确的事务边界、唯一约束及必要的条件更新。

例如，需要对所有服务实例共享的登录接口进行限流，每秒最多允许 100 次请求。

六、队列：异步任务与延迟处理

6.1 RBlockingQueue：阻塞队列

put()、take() 适合生产者消费者模式；offer()、poll() 适合不希望一直等待的场景。

在 Spring Boot 项目中，实际使用时应将生产者、消费者分开设计，避免在 HTTP 请求线程里直接无限阻塞消费。

典型场景包括延迟通知、超时检查和定时触发。但是，延迟队列本身并不意味着业务只执行一次。如果任务处理失败、消费者重启或消息被重复处理，仍然需要幂等性设计。

七、发布订阅：RTopic

适合跨实例广播简单通知，例如配置刷新提醒、事件通知。

Redisson 为 Redis 提供了 Topic 和其他消息相关 API。

这里最容易混淆的是：普通 Redis Pub/Sub 不是可靠消息队列。 离线的订阅者不会自动收到它离线期间错过的历史消息。因此它适合广播通知，不适合独自承担不能丢失的业务任务。

八、信号量与分布式任务同步

8.1 RSemaphore：限制并发数

例如，一个外部服务最多允许 10 个并发任务访问。

RSemaphore 适合限制整体并发任务数，而不只是请求频率。Redisson 也提供带租期的许可信号量等同步器。

注意：共享许可的初始化应当只由受控流程完成；不能每次请求到来时都重新初始化许可数，否则就会破坏并发限制。

另外，与 RLock 不同，普通信号量的许可通常可以由另一个线程释放。但这也意味着必须确保每一次成功申请最终只释放一次，否则会多出不存在的并发容量。

十、布隆过滤器：RBloomFilter

当需要判断某个元素是否可能出现过，并且可以接受一定误判时，可以使用布隆过滤器。

典型用途：在查询数据库前，快速判断一个 ID 是否可能存在，从而减少部分无效查询。

需要准确理解布隆过滤器的性质：

  • false 通常意味着元素不在集合中。

  • true 表示元素可能存在，不代表一定存在。

  • 不能把它作为数据库唯一性约束。

  • 要根据容量和期望误判率进行初始化规划。

Redisson 的概率型数据结构还包括 HyperLogLog 等。

十一、异步 API 与批量操作

11.1 异步操作

Redisson 提供了异步 API，适合不希望同步等待 Redis 响应的调用链。

不同 API 对应的返回类型有所区别，例如 RFuture<T>。在使用异步锁时还需要额外注意线程所有权：一个逻辑操作可能跨越多个线程，所以获取锁与释放锁时必须正确处理线程 ID。

11.2 RBatch：批量执行

当需要对 Redis 执行多条独立操作时，可以考虑批处理，减少逐条请求的网络往返。

批处理适合批量读写，不过需要注意：

批处理不等于业务事务。 如果多条操作必须作为整体提交，需要另外评估 Redisson 的事务 API、Redis 的执行语义，以及与 MySQL 之间的一致性需求。

十二、生产环境必须注意的问题

  1. 客户端生命周期

让 RedissonClient 由 Spring 管理并在应用退出时关闭。避免在 Service 方法、请求入口或定时任务内部反复 Redisson.create()。

  1. 锁的粒度和释放

锁名应当与具体业务资源绑定，临界区应尽量短；等待超时、固定租约、看门狗续期和异常释放需要一起考虑。

  1. 缓存与数据库一致性

Redis 里的缓存对象不是数据库事实来源的替代品。要设计过期、更新、删除、并发写入和缓存击穿等问题的处理方式。

  1. 连接和阻塞控制

关注 Redis 延迟、连接池利用率、超时、重连和线程池占用。阻塞队列、acquire() 以及同步等待都可能影响业务线程的可用性。

  1. 序列化与版本兼容

跨服务共享对象时，要确保 Codec 与对象结构兼容。谨慎处理类名、字段变更以及不同部署版本之间的数据格式差异。

这些并不是 Redisson 特有的全部问题，而是将 Redis 用在分布式系统里必须面对的工程问题。Redisson 提供了丰富的原语，但不意味着用了 API 就自动获得业务层的强一致性或可靠投递保证。
